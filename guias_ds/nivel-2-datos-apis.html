Datos y APIs: cómo se guardan y cómo se piden

En el Nivel 1 dibujaste qué hace TurnoYa, cómo se llaman sus piezas y qué estados tiene cada turno. Pero todavía todo vive en la memoria de un solo programa. Este nivel baja al terreno de los datos y las conexiones: dónde se guardan de verdad (tablas o documentos), cómo otras aplicaciones los piden (APIs REST), cómo cambiar esa conversación sin romper a quien ya la usa, y cómo evitar que un reintento duplique una operación.

👁 — vistas · Ing. Roy Carrasco, Facultad de Ingeniería de Sistemas · UAB

Seguís acompañando a Diego en TurnoYa. Si todavía no hiciste el Nivel 1B, conviene empezar por ahí. Todo se explica desde cero: solo hace falta saber programar lo básico. En cada decisión podés probar primero un camino equivocado, ver su consecuencia sin penalidad, y recién después se desbloquea el correcto.

¿Dónde viven los turnos?

Hasta ahora TurnoYa guarda los turnos en una variable dentro del servidor: si se reinicia, se pierden todos. Diego tiene que elegir dónde guardarlos de verdad. Los datos son claros: estudiante, fotocopiadora y horario. Y las reglas también: un horario de una fotocopiadora no se puede reservar dos veces, y cada turno tiene que apuntar a un estudiante que exista.

Lo que está en juego

No alcanza con guardar los datos: hay que decidir quién garantiza que las reglas se cumplan, incluso cuando dos estudiantes tocan "reservar" al mismo tiempo.

Decisión

¿Qué tipo de almacenamiento elige Diego?

Un archivo no sabe nada de las reglas: si dos peticiones llegan a la vez, las dos pueden escribir la misma línea, y nada impide un turno con un estudiante inexistente. Probá con otra opción.

Una copia diaria significa que, ante una caída, se pierde hasta un día entero de turnos. Y la variable sigue sin garantizar ninguna regla de las que importan. Probá con otra opción.

Correcto. Una base relacional puede rechazar por sí sola un horario repetido o un estudiante inexistente, aunque el código de la aplicación tenga un error. Seguí leyendo ↓

El modelo relacional: tablas, claves y reglas que se cumplen solas

En una base relacional los datos se guardan en tablas: cada fila es un registro y cada columna un dato. Las tablas se conectan entre sí mediante claves, y la base misma hace cumplir las reglas que declarás.

ConceptoQué esEjemplo en TurnoYa
Clave primaria (PK)La columna que identifica cada fila de forma única.El id de cada turno.
Clave foránea (FK)Una columna que apunta a la fila de otra tabla y obliga a que esa fila exista.estudiante_id en turno apunta a estudiante.
Restricción UNIQUEProhíbe que dos filas repitan la misma combinación de valores.Una fotocopiadora no puede tener dos turnos con el mismo inicio.
TransacciónUn grupo de cambios que se aplican todos juntos o no se aplica ninguno.Crear el turno y descontar el cupo, o ninguna de las dos cosas.

Así quedaría la tabla de turnos. No hace falta que memorices la sintaxis: mirá cómo cada regla del enunciado es una línea.

SQL — tabla turno
CREATE TABLE turno (
  id               SERIAL PRIMARY KEY,
  estudiante_id    INT NOT NULL REFERENCES estudiante(id),
  fotocopiadora_id INT NOT NULL REFERENCES fotocopiadora(id),
  inicio           TIMESTAMP NOT NULL,
  estado           TEXT NOT NULL DEFAULT 'solicitado',
  UNIQUE (fotocopiadora_id, inicio)
);
Del diagrama de clases a las tablas

Cada clase del Nivel 1A suele convertirse en una tabla, sus atributos en columnas, y cada relación entre clases en una clave foránea. El diagrama de clases ya era la "vista de datos" de TurnoYa.

El menú que no cabe en una tabla

La cafetería del campus quiere sumar su menú a TurnoYa. Cada producto tiene atributos distintos: un café tiene tamaño, tipo de leche y temperatura; un sándwich tiene ingredientes y si es vegetariano; un combo es una lista de otros productos con descuento. El dueño agrega un tipo nuevo de producto casi todas las semanas, y la app siempre muestra cada producto completo, con todos sus datos juntos.

Decisión

¿Cómo guarda Diego el menú?

La tabla termina con decenas de columnas casi siempre vacías, y cada tipo nuevo obliga a modificar la estructura de toda la tabla. Funciona, pero pelea contra la forma de los datos. Probá con otra opción.

Una tabla por tipo obliga a crear estructura nueva cada semana y complica leer "todo el menú" de una sola vez, que es justo lo que la app hace siempre. Probá con otra opción.

Correcto. Cada producto es un documento autocontenido con su propia forma, que se guarda y se lee entero de una sola vez — justo el patrón del menú. Seguí leyendo ↓

El modelo de documentos: cada registro lleva su propia forma

En una base de documentos cada registro es un documento, normalmente JSON, que puede tener campos anidados y distintos a los de otros documentos de la misma colección.

JSON — dos productos del menú
{ "_id": "cafe-01", "tipo": "cafe",
  "nombre": "Cortado", "tamanos": ["chico", "grande"],
  "leche": ["entera", "deslactosada"], "caliente": true }

{ "_id": "sand-07", "tipo": "sandwich",
  "nombre": "Milanesa completa",
  "ingredientes": ["milanesa", "lechuga", "tomate"],
  "vegetariano": false }
AspectoRelacionalDocumentos
EstructuraFija y declarada de antemano para toda la tabla.Flexible: cada documento puede tener la suya.
Relaciones y reglasLa base las hace cumplir (claves foráneas, UNIQUE).Quedan mayormente a cargo de la aplicación.
Lectura típicaCombinar datos de varias tablas.Leer un documento completo de una sola vez.
Conviene cuandoLas reglas entre datos son estrictas y críticas.La forma varía o los datos se leen siempre juntos.
No hay un ganador general

Se elige por la forma de los datos y por las reglas que hay que garantizar. Un sistema real puede usar los dos a la vez: turnos y pagos en relacional, menú y registro de eventos en documentos.

Clasificación

¿Qué modelo conviene para cada dato?

Pagos, donde cada pago debe apuntar a un pedido y a un estudiante que existan.
Preferencias de perfil, con opciones distintas según cada persona.
Reservas de turnos, donde ningún horario puede quedar ocupado dos veces.
Registro de eventos de la app (clics, errores), con campos que cambian según el evento.
Inventario de insumos, donde cada venta descuenta cantidades sin perder ni duplicar nada.
Fichas de promociones de distinto tipo, que siempre se leen completas de una sola vez.

"¿Cómo le pido al servidor que cancele un turno?"

La app móvil de los estudiantes necesita hablar con el servidor de TurnoYa. Diego tiene que definir cómo se ve la petición para cancelar un turno. Acordate del Nivel 1B: un turno cancelado no desaparece, pasa al estado "cancelado", y solo se puede cancelar desde ciertos estados.

Decisión

¿Cómo expone Diego la cancelación?

Poner el verbo en la ruta y crear una nueva por cada acción lleva a decenas de rutas sueltas sin un patrón. Además no deja claro qué recurso se está modificando. Probá con otra opción.

Borrar el turno destruye el historial: nadie podría saber cuántos turnos se cancelaron ni por qué. Y además contradice el diagrama de estados, donde "cancelado" es un estado más. Probá con otra opción.

Correcto. El turno es el recurso, el verbo dice qué se hace con él, y el servidor aplica las reglas del diagrama de estados. Seguí leyendo ↓

APIs REST: recursos con nombre, verbos con significado

Una API es el acuerdo mediante el cual un programa le pide cosas a otro. En una API REST sobre HTTP, la ruta nombra un recurso (un sustantivo, como /turnos) y el verbo HTTP dice qué hacer con él.

VerboQué haceEjemplo
GETLee, sin modificar nada.GET /turnos/7
POSTCrea un recurso nuevo.POST /turnos
PUT / PATCHReemplaza o modifica parte de un recurso.PATCH /turnos/7
DELETEElimina el recurso.DELETE /turnos/7
HTTP — cancelar el turno 7
PATCH /turnos/7
Content-Type: application/json

{ "estado": "cancelado" }

--- respuesta si el turno estaba "confirmado" ---
200 OK
{ "id": 7, "estado": "cancelado" }

--- respuesta si el turno ya estaba "atendido" ---
409 Conflict
{ "error": "No se puede cancelar un turno atendido" }
CódigoCuándo usarlo
200 OK / 201 CreatedLa operación salió bien / se creó el recurso.
400 Bad RequestLa petición está mal armada (falta un campo, formato inválido).
404 Not FoundEl recurso pedido no existe.
409 ConflictLa petición choca con el estado actual (por ejemplo, cancelar un turno ya atendido).
Un endpoint gordo o varios

Evitá el endpoint único tipo POST /accion con un campo "tipo" que decide qué hacer: no se puede documentar, ni cachear, ni devolver códigos claros. Varios endpoints chicos, uno por recurso, se entienden solos.

Emparejamiento

Une cada petición o código con su significado.

"La hora vieja trae bugs, pero la app ya está instalada"

Las respuestas de la API traen la hora del turno como un texto suelto, "hora": "10:30", sin fecha ni zona horaria — y eso ya causó confusiones. Diego quiere cambiarlo por un campo inicio con fecha y hora completas. El problema: la versión 1 de la app ya está instalada en cientos de celulares, y muchos estudiantes no actualizan.

Decisión

¿Cómo publica Diego el cambio?

Apenas se renombra el campo, la app v1 deja de encontrar "hora" y se rompe para todos los que no actualizaron. Un aviso por chat no llega a todos, y la rotura es inmediata. Probá con otra opción.

Congelar el contrato para siempre protege a los clientes viejos, pero deja el bug para todos, incluidos los clientes nuevos. Existe una forma de mejorar sin romper a nadie. Probá con otra opción.

Correcto. Con dos versiones conviviendo, los clientes nuevos usan el contrato mejorado y los viejos siguen funcionando mientras migran. Seguí leyendo ↓

Contratos y versionado: no rompas a quien ya te usa

El contrato de una API es lo que prometés: rutas, nombres de campos, tipos de dato y códigos de respuesta. Cualquier aplicación que ya lo use depende de cada detalle, aunque nunca lo hayas visto.

Tipo de cambioEfecto en clientes existentesEjemplos
CompatibleLos clientes viejos siguen funcionando sin tocar nada.Agregar un campo opcional a la respuesta; agregar un endpoint nuevo.
IncompatibleAlgún cliente viejo se rompe.Renombrar o quitar un campo; cambiar su tipo; volver obligatorio algo que era opcional.
La regla práctica

Los cambios compatibles se publican sin más. Los incompatibles necesitan una versión nueva (/v2/...) y un plazo de convivencia con la anterior. Una forma de versionar es poner el número en la ruta; otra es mandarlo en un encabezado, pero el principio es el mismo.

Clasificación

¿Es un cambio compatible o incompatible?

Agregar un campo opcional "notas" a la respuesta de un turno.
Renombrar el campo "hora" a "inicio" en todas las respuestas.
Agregar un endpoint nuevo, GET /fotocopiadoras, que antes no existía.
Cambiar "estudiante_id" de un número a un texto.
Volver obligatorio un campo que antes se podía omitir al crear un turno.
Devolver más datos en el detalle del turno, sin quitar ninguno de los anteriores.

Tres cafés por un solo toque

En un pasillo con mala señal, una estudiante toca "Pedir" para encargar un café en la cafetería. No ve respuesta y vuelve a tocar. Además, la app reintenta sola cuando no recibe respuesta. Resultado: POST /pedidos llegó tres veces, y a ella le cobraron tres cafés.

Decisión

¿Cómo evita Diego los pedidos duplicados?

Deshabilitar el botón ayuda con los toques repetidos, pero no con los reintentos automáticos de la red ni con una petición que se reenvía sola. El servidor sigue sin poder distinguir un reintento de un pedido nuevo. Probá con otra opción.

Un cartel no frena los reintentos que hace la app sola, y revisar a mano cada mañana llega siempre después del cobro. El problema se corrige a mano cuando debió evitarse en el diseño. Probá con otra opción.

Correcto. Con una clave de idempotencia, el servidor reconoce un reintento y devuelve el resultado de la primera vez en lugar de crear otro pedido. Seguí leyendo ↓

Idempotencia: pedir lo mismo dos veces sin efectos dobles

Una operación es idempotente si repetirla deja el sistema en el mismo estado final que hacerla una sola vez. En una red real los mensajes se pierden y se reenvían, así que esta propiedad no es un lujo.

Verbo¿Idempotente?Por qué
GETSíSolo lee: leer diez veces no cambia nada.
PUTSíReemplaza el recurso con los mismos datos; el resultado final es igual.
DELETESíDespués del primer borrado, el recurso ya no existe; repetir no cambia ese estado.
POSTNoCada llamada crea un recurso nuevo, salvo que se la proteja.

Para proteger un POST, el cliente genera una clave única por intento lógico y la manda en cada reintento:

HTTP — pedido con clave de idempotencia
POST /pedidos
Idempotency-Key: 7f3a-91c2-4d10
Content-Type: application/json

{ "producto": "cafe-01", "cantidad": 1 }

--- primera vez ---
201 Created   { "id": 412, "estado": "recibido" }

--- reintento con la MISMA clave ---
200 OK        { "id": 412, "estado": "recibido" }   (mismo pedido)
Completar

1. Hacer un PUT dos veces con los mismos datos deja el recurso igual que hacerlo una vez, por eso PUT es .

2. Un POST /pedidos repetido, sin ninguna protección, crea .

3. Para que el servidor reconozca un reintento, el cliente envía una .

4. Si llega una petición con una clave que ya se usó, el servidor responde con .

De vuelta con la IA: ¿qué le pasa Diego esta vez?

Diego le pide a una IA: "hacé el endpoint para reservar un turno". Devuelve una ruta POST /reservarTurno, un campo userId que no existe en ninguna tabla, una tabla con nombres distintos a los acordados, y una respuesta 200 para absolutamente todo, incluso cuando el horario ya estaba ocupado.

Decisión

¿Qué le da Diego a la IA para el próximo intento?

Con solo un nombre, la IA vuelve a rellenar los huecos con lo que le parezca típico: nombres de campos, códigos de error, reintentos. Es el mismo problema de antes con un mejor título. Probá con otra opción.

"Profesional" y "seguro" no son verificables: la IA los interpreta como quiera y los nombres siguen sin coincidir con tu base de datos. Más palabras no son más precisión. Probá con otra opción.

Correcto. Un esquema y un contrato concretos eliminan los huecos donde la IA inventa. Cerrás el recorrido del nivel. Seguí leyendo ↓

Qué le das a la IA para que no invente el contrato

Cada error típico de una IA al generar una API tiene un material concreto que lo previene. La clave es reconocer el error para saber qué pasarle.

Lo que falla en el código generadoQué pasarle a la IA
Inventa nombres de campos, tablas o columnas.El esquema de tablas exacto y un ejemplo de JSON real.
Rutas con verbos (/reservarTurno) o verbos HTTP equivocados.La lista de rutas con su verbo, ya decidida por el equipo.
Responde 200 para todo.Una tabla con el código de estado esperado para cada caso.
Ignora los reintentos y crea duplicados.La regla de idempotencia escrita explícitamente.

Un prompt con contrato se ve así:

Prompt — contrato para la IA
Implementá POST /turnos.
Tabla: turno(id, estudiante_id, fotocopiadora_id, inicio, estado)
  con UNIQUE(fotocopiadora_id, inicio).
Entrada:  { "estudiante_id": 5, "fotocopiadora_id": 2,
            "inicio": "2026-10-05T10:30:00-04:00" }
Salida:   201 { "id": 7, "estado": "solicitado" }
Errores:  400 si falta un campo; 404 si el estudiante
          no existe; 409 si el horario ya está ocupado.
Reintentos: si llega la misma Idempotency-Key, devolver
          el turno ya creado con 200.
No agregues campos ni rutas que no estén acá.
Lo que sigue siendo tuyo

Decidir el contrato —nombres, códigos, qué cambios son compatibles— es una decisión de diseño. La IA no tiene forma de saber qué aplicaciones ya instaladas dependen de tu API; eso solo lo sabés vos.

Checklist de autoevaluación
  • La elección relacional/documentos se justifica por la forma de los datos o las reglas a garantizar, no por moda.
  • Las rutas nombran recursos (sustantivos) y el verbo HTTP expresa la acción; no hay /crearAlgo.
  • Cada endpoint tiene al menos un código de éxito y uno de error distinto de 200, con su motivo.
  • El cambio incompatible elegido tiene un plan de versión y convivencia, no un "avisamos y listo".
  • La operación idempotente identifica qué se repite y qué clave o regla evita el efecto doble.
  • El prompt incluye esquema, entrada, salida, errores y la instrucción de no inventar nada fuera del contrato.

¿Sabías que...?

🗄️ El modelo relacional tiene más de 50 años

Edgar Codd lo propuso en 1970, trabajando en IBM. La idea de organizar datos en tablas relacionadas por claves sigue siendo la base de los motores relacionales que se usan hoy.

🌐 REST salió de una tesis doctoral

Roy Fielding definió REST en su tesis del año 2000, describiendo por qué la web había escalado tan bien. Muchas "APIs REST" actuales siguen solo una parte de esas ideas, y igual resultan útiles.
