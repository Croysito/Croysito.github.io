Arquitectura y patrones: cómo se organiza el sistema entero

En el Nivel 2 decidiste cómo se guardan los datos y cómo se piden. Ahora toca mirar el conjunto: cómo organizar el código para que cambiar la base de datos no toque las reglas, si conviene partir el sistema en servicios, cómo sacar de la petición lo que tarda, cómo acelerar lecturas con cache, y cómo pedirle a una IA que respete la estructura que armaste. Todo con el criterio de un equipo chico: usar solo la complejidad que se necesita.

👁 — vistas · Ing. Roy Carrasco, Facultad de Ingeniería de Sistemas · UAB

Seguís acompañando a Diego en TurnoYa. Si todavía no hiciste el Nivel 2, conviene empezar por ahí. Todo se explica desde cero: solo hace falta saber programar lo básico (los ejemplos están en Python). En cada decisión podés probar primero un camino equivocado, ver su consecuencia sin penalidad, y recién después se desbloquea el correcto.

Cambiar la base de datos no debería tocar las reglas

TurnoYa guarda todo en SQLite, pero el hosting gratuito termina y hay que pasar a PostgreSQL. Diego abre el código y encuentra algo que no esperaba: la regla "un turno no se puede reservar si el horario está ocupado" está escrita dentro del controlador de la API, mezclada con consultas SQL propias de SQLite. Cambiar de base significa tocar —y volver a probar— las reglas del negocio.

Lo que está en juego

Cuando las reglas del negocio dependen de detalles como la base de datos o el framework web, cambiar cualquiera de esos detalles es caro y arriesga romper lo que ya funcionaba.

Decisión

¿Cómo reorganiza Diego el código?

Duplicar el controlador deja la misma regla en dos lugares: cuando cambie, hay que acordarse de tocar las dos. Se resolvió el cambio de base de hoy y se empeoró el de mañana. Probá con otra opción.

Mover las reglas a la base las ata todavía más a ese motor: el próximo cambio sería otra reescritura, y probar las reglas exigiría levantar una base real. Probá con otra opción.

Correcto. Esa es la idea de la arquitectura limpia (o hexagonal): el núcleo con las reglas no conoce los detalles, y los detalles dependen de él. Seguí leyendo ↓

Arquitectura limpia: capas y la regla de dependencia

La arquitectura limpia organiza el código en capas concéntricas. Lo que cambia poco y vale mucho (las reglas del negocio) va en el centro; lo que cambia seguido (framework, base, servicios externos) va afuera. Una sola regla lo sostiene: el código de adentro nunca importa al de afuera.

CapaQué contieneEn TurnoYa
DominioEntidades y reglas del negocio. No importa nada externo.Turno; "un horario no se reserva dos veces".
AplicaciónCasos de uso: orquestan el dominio para lograr una meta.ReservarTurno, CancelarTurno.
InfraestructuraDetalles técnicos: API, base, servicios externos.Rutas HTTP, PostgreSQL, el envío de WhatsApp.
No hace falta usar estos nombres

Algunos equipos hablan de "hexagonal", "puertos y adaptadores" u "onion". Los nombres cambian; lo que importa es la dirección de las dependencias. Si podés cambiar la base sin tocar una sola regla, estás en lo correcto.

Clasificación

¿En qué capa va cada pieza?

Un turno no puede empezar en el pasado.
El código que arma el JSON de respuesta de GET /turnos.
ReservarTurno: busca el horario, verifica que esté libre, guarda el turno y pide el aviso.
La consulta SQL que trae los turnos de una fotocopiadora.
Un estudiante con tres turnos pendientes no puede reservar otro.
CancelarTurno: carga el turno, lo cancela y guarda el resultado.

El caso de uso necesita guardar el turno

Diego ya separó las capas. Ahora escribe ReservarTurno, que necesita guardar el turno. Lo primero que se le ocurre es importar la librería de PostgreSQL dentro del caso de uso, y listo. Pero Tomás le marca dos problemas: la capa de aplicación acaba de depender de la base —al revés de la regla— y para probar el caso de uso hará falta una base real encendida.

Decisión

¿Cómo lo resuelve Diego?

Correcto. Eso es invertir la dependencia: el núcleo declara qué necesita (un puerto) y la infraestructura se adapta a eso. Seguí leyendo ↓

Una función auxiliar que sigue importando la librería deja la dependencia donde estaba: la capa de aplicación todavía no puede probarse ni usarse sin esa base. Cambió el aspecto, no la dirección. Probá con otra opción.

Hace lo opuesto: el núcleo pasa a depender del framework, un detalle que cambia más seguido que las reglas. Es justamente lo que la regla de dependencia prohíbe. Probá con otra opción.

Puertos y adaptadores: invertir la dependencia

Un puerto es la descripción de lo que el núcleo necesita ("guardá este turno"). Un adaptador es el código de afuera que cumple esa descripción con una tecnología concreta (PostgreSQL, una lista en memoria). Mirá cómo quedan las flechas de import.

Python — el núcleo define el puerto
# dominio/turno.py  (núcleo: no importa nada de afuera)
class Turno:
    def __init__(self, estudiante_id, fotocopiadora_id, inicio):
        self.estudiante_id = estudiante_id
        self.fotocopiadora_id = fotocopiadora_id
        self.inicio = inicio
        self.estado = "solicitado"

# aplicacion/puertos.py  (lo que el caso de uso NECESITA, sin decir cómo)
class RepositorioDeTurnos:
    def horario_libre(self, fotocopiadora_id, inicio): ...
    def guardar(self, turno): ...

# aplicacion/reservar_turno.py
class ReservarTurno:
    def __init__(self, repo):              # recibe el puerto, no una base concreta
        self.repo = repo

    def ejecutar(self, estudiante_id, fotocopiadora_id, inicio):
        if not self.repo.horario_libre(fotocopiadora_id, inicio):
            raise ValueError("Horario ocupado")
        turno = Turno(estudiante_id, fotocopiadora_id, inicio)
        self.repo.guardar(turno)
        return turno
Python — los adaptadores lo cumplen
# infraestructura/repo_postgres.py  (adaptador: cumple el puerto con PostgreSQL)
class RepoPostgres(RepositorioDeTurnos):
    def __init__(self, conexion):
        self.conexion = conexion
    def horario_libre(self, fotocopiadora_id, inicio): ...   # SELECT real
    def guardar(self, turno): ...                            # INSERT real

# pruebas/repo_en_memoria.py  (otro adaptador: una lista, sin base de datos)
class RepoEnMemoria(RepositorioDeTurnos):
    def __init__(self):
        self.turnos = []
    def horario_libre(self, fotocopiadora_id, inicio):
        return all(not (t.fotocopiadora_id == fotocopiadora_id and t.inicio == inicio)
                   for t in self.turnos)
    def guardar(self, turno):
        self.turnos.append(turno)

# La misma regla se prueba en milisegundos, sin levantar ninguna base:
caso = ReservarTurno(RepoEnMemoria())
Qué se gana

Cambiar PostgreSQL por otra base es escribir un adaptador nuevo, sin tocar ReservarTurno. Y las reglas se prueban con una lista en memoria, en milisegundos. En Python no hace falta una palabra especial para "interfaz": una clase base con métodos vacíos alcanza. Lo importante es quién importa a quién.

"Netflix usa microservicios"

Tomás vio una charla y propone separar TurnoYa en cuatro servicios independientes: turnos, usuarios, notificaciones y pagos. Hoy el equipo son tres developers, hay una sola aplicación y un solo servidor. Le piden a Diego una recomendación.

Decisión

¿Qué recomienda Diego?

Cada servicio suma despliegue, red entre ellos, datos repartidos y monitoreo propios. Con tres personas, el tiempo se iría en operar la infraestructura y no en mejorar TurnoYa, para escalar un problema que todavía no existe. Probá con otra opción.

Correcto. Un monolito modular da casi todo el orden con una fracción de la complejidad operativa. Si un módulo lo pide, se extrae después. Seguí leyendo ↓

Sin límites internos el código se enreda, cada cambio toca todo y, el día que haga falta separar algo, no habrá por dónde cortar. Una sola aplicación no es lo mismo que una aplicación sin orden. Probá con otra opción.

Monolito modular vs. microservicios

Un monolito se despliega como una sola pieza; los microservicios son varias aplicaciones chicas que se hablan por red. La diferencia más grande no es técnica sino de costo: cada servicio nuevo es otro programa que desplegar, vigilar y mantener sincronizado.

AspectoMonolito modularMicroservicios
DespliegueUna sola pieza.Una pieza por servicio, cada una con su proceso.
ComunicaciónLlamada a una función: instantánea y no falla.Llamada por red: tarda y puede fallar.
DatosUna base: una transacción cubre todo.Una base por servicio: mantener todo coherente es difícil.
Equipo idealPocas personas, un solo ritmo.Muchos equipos que necesitan desplegar sin esperarse.
Un problema de organización antes que técnico

Los microservicios resuelven sobre todo el trabajo de muchos equipos grandes sobre el mismo producto. Para un equipo de tres, casi siempre agregan costo sin dar nada a cambio. Lo habitual es empezar por un monolito modular y separar un módulo solo cuando hay una razón concreta.

Clasificación

¿Qué arquitectura sugiere cada situación?

Un equipo de tres personas lanza la primera versión de la app.
Veinte equipos necesitan publicar cambios sin esperarse entre sí.
Una sola base garantiza que un turno y su pago se guarden juntos o ninguno.
El envío masivo de mensajes necesita escalar cincuenta veces más que el resto.
Todavía no se sabe qué partes van a crecer ni cuánto.
Un módulo lo mantiene otra organización y se publica con su propio ciclo de versiones.

El WhatsApp que tarda tres segundos

Al confirmar un turno, la API envía un WhatsApp de aviso antes de responder. El servicio de mensajes tarda unos tres segundos y a veces falla; cuando falla, el estudiante ve un error aunque el turno sí se guardó. Hay quejas de gente que reserva dos veces por las dudas.

Decisión

¿Cómo lo rediseña Diego?

Correcto. Lo secundario y lento sale de la petición: la respuesta es inmediata y el aviso llega después, con reintentos si falla. Seguí leyendo ↓

Ahora el estudiante no puede reservar cada vez que el servicio de mensajes esté caído: una función secundaria pasó a bloquear la principal, y puede enviarse un aviso de un turno que luego no se guarda. Probá con otra opción.

Un error más rápido sigue siendo un error: el turno se guarda igual, el estudiante ve un fallo y el aviso se pierde. Acortar la espera no cambia que dos cosas distintas están atadas. Probá con otra opción.

Colas y eventos: no hacer esperar a quien no tiene que esperar

Una cola guarda mensajes hasta que otro proceso (el consumidor) los tome. Un evento es un mensaje que cuenta algo que ya pasó ("TurnoConfirmado"). Quien lo publica no sabe ni le importa quién lo escucha, y esa separación es lo que permite responder rápido.

Python — publicar y consumir
# En la petición HTTP (rápida): guardar y publicar el evento
turno = reservar_turno.ejecutar(estudiante_id, fotocopiadora_id, inicio)
cola.publicar("TurnoConfirmado", {"turno_id": turno.id})
return {"id": turno.id}, 201            # el estudiante ya tiene su respuesta

# En un proceso aparte (worker), que lee la cola:
def al_recibir(evento):
    if ya_enviado(evento["turno_id"]):  # idempotente: un reintento no duplica el aviso
        return
    enviar_whatsapp(evento["turno_id"])
    marcar_enviado(evento["turno_id"])
Costo o ventajaQué significa
Respuesta rápidaEl estudiante no espera por lo que no necesita para seguir.
Consistencia eventualEl aviso llega unos segundos después del turno, no a la vez.
ReintentosSi el envío falla, la cola vuelve a intentarlo sin molestar a nadie.
Mensajes repetidosCon reintentos, un mensaje puede entregarse más de una vez.
Se conecta con el Nivel 2

Como un mensaje puede llegar dos veces, el consumidor tiene que ser idempotente: repetirlo no debe duplicar el efecto. Es la misma idea de la Idempotency-Key que viste con las APIs, aplicada ahora a las colas.

4. Que el aviso llegue unos segundos después del turno se llama consistencia .

200 consultas por minuto para la misma respuesta

En hora pico, unos 200 estudiantes por minuto abren la pantalla "horarios libres", y cada vez la API ejecuta una consulta pesada contra la base. La base se pone lenta y, con ella, también las reservas. Los horarios libres cambian apenas unas pocas veces por minuto.

Decisión

¿Qué hace Diego?

Sin vencimiento ni borrado, el cache muestra para siempre lo que estaba libre cuando se guardó: los estudiantes verían libres turnos ya tomados y fallarían al reservar. Probá con otra opción.

Pagar más resuelve hoy y deja intacto el motivo: 200 consultas iguales por minuto para una respuesta que casi no cambia. Es un gasto fijo para evitar una complejidad que tiene solución chica. Probá con otra opción.

Correcto. Un tiempo de vida corto (TTL) limita cuánto puede estar desactualizado el dato, y borrarlo al cambiar evita mostrar horarios ya tomados. Seguí leyendo ↓

Cache: responder de memoria lo que casi no cambia

Un cache es una copia rápida de un resultado costoso. Mientras la copia sirva, la base no se toca. El problema no es guardarla, sino saber cuándo deja de ser válida.

TérminoQué significa
Acierto (hit)El dato estaba en el cache y se respondió de memoria.
Fallo (miss)No estaba: se consulta la base y se guarda el resultado.
TTLTiempo de vida: tras ese tiempo la copia se descarta sola.
InvalidaciónBorrar la copia a propósito cuando el dato original cambia.
Cachear para mostrar, no para decidir

La pantalla "horarios libres" tolera mostrar un dato de hace 30 segundos. Pero el momento de reservar no: ahí la regla siempre consulta la fuente de verdad (la base). Cachear sirve para lecturas masivas que toleran un poco de atraso, no para validar reglas que deben ser exactas.

Patrones de diseño y arquitectura con IA

Un patrón de diseño es una solución con nombre a un problema que se repite. No se aplica para "tener patrones": se reconoce cuando el problema aparece. Y como una IA conoce muchos, nombrarlos en el prompt le acota mucho el resultado.

PatrónProblema que resuelveEn TurnoYa
RepositoryEsconder dónde y cómo se guardan los datos detrás de una interfaz.RepositorioDeTurnos, el puerto que viste.
AdapterHacer que algo con otra interfaz encaje en la que tu código espera.Envolver la API de WhatsApp en enviar_aviso().
StrategyIntercambiar distintas formas de hacer lo mismo.Calcular el recargo por cancelar tarde de varias maneras.
ObserverAvisar a varios interesados sin que quien avisa los conozca.Los eventos como TurnoConfirmado.

Un prompt de arquitectura incluye cuatro cosas: la estructura, la regla de dependencia, lo que ya existe y lo que no debe inventar.

infraestructura/ (API, base de datos, WhatsApp).
Regla de dependencia: dominio no importa nada; aplicacion solo importa dominio;
infraestructura puede importar a ambas.

Checklist de autoevaluación
  • El dominio no nombra ninguna tecnología (base, framework, servicio externo); esos detalles están todos en infraestructura.
  • El puerto lo define el núcleo según lo que necesita, no según lo que ofrece la tecnología que lo va a implementar.
  • La decisión monolito/microservicios se justifica con el tamaño del equipo y un problema concreto, no con "es lo que usan las empresas grandes".
  • El evento está nombrado en pasado, y se explica cómo evita el consumidor efectos duplicados si recibe el mensaje dos veces.
  • El dato cacheado es de lectura masiva y tolera atraso; el dato que no se cachea necesita exactitud al instante, y se justifica por qué.
  • El prompt incluye la estructura de capas, la regla de dependencia, lo que ya existe y una instrucción explícita de no inventar nada más.

⬡ La arquitectura hexagonal es de 2005

Alistair Cockburn la describió con el nombre de "puertos y adaptadores". Robert C. Martin popularizó una versión parecida como "Clean Architecture" a partir de 2012. Las dos comparten la misma regla de dependencia.

🧠 "Solo hay dos cosas difíciles"

Una frase atribuida a Phil Karlton dice que en informática solo hay dos cosas realmente difíciles: invalidar un cache y ponerle nombre a las cosas. Después de este nivel, ya sabés por qué la primera tiene fama.
