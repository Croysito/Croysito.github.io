1. json, jsonb y los tipos de valor

Antes de consultar nada, comprueba con tus propios ojos qué hace jsonb con lo que le entregas, y qué rechaza.

Enunciado — 1.1: json frente a jsonb

Escribe un SELECT con dos columnas, como_json y como_jsonb, que conviertan el mismo literal {"a":1, "b":2, "a":3} (con los espacios y la clave a repetida) al tipo json y al tipo jsonb con ::.

🗄️ Ejercicio 1.1 — json y jsonb lado a lado
Resultado
Dos resultados distintos

El json conservó el texto tal cual: espacios, orden y las dos a. El jsonb quedó como {"a": 3, "b": 2}: una sola a (gana la última) y sin los espacios.

Enunciado — 1.2: el CHECK en acción (debe fallar)

Intenta insertar en productos una fila de nombre Cosa rara, precio 10 y atributos [1,2] (un arreglo, no un objeto). Debería fallar.

🗄️ Ejercicio 1.2 — INSERT con un arreglo en atributos
Resultado
Error esperado

Deberías ver new row for relation "productos" violates check constraint "atributos_es_objeto". Es el CHECK que escribiste en "Prepara tu base de datos": solo deja pasar objetos.

Enunciado — 1.3: los seis tipos de valor

Con jsonb_typeof sobre literales ::jsonb, consulta el tipo de estos seis valores en un solo SELECT: 16, "16", true, null, {"gb":512} y ["HDMI"].

🗄️ Ejercicio 1.3 — jsonb_typeof de seis valores
Resultado
Seis tipos distintos

Deberías ver, en orden: number, string, boolean, null, object y array. Fíjate en los dos primeros: 16 y "16" parecen lo mismo, pero para jsonb son tipos distintos. Eso vuelve en la sección 3.

2. Leer: ->, ->> y #>>

Sacar un valor del documento es fácil. Lo difícil es acordarse de qué tipo devuelve cada operador.

Enunciado — 2.1: flecha simple frente a doble

Lista nombre, la marca con -> (columna con_flecha) y la marca con ->> (columna con_doble_flecha) de todos los productos, ordenados por id.

🗄️ Ejercicio 2.1 — -> frente a ->>
Resultado
Con y sin comillas

La columna con_flecha conserva las comillas ("Lenovo") porque sigue siendo JSON; con_doble_flecha es texto SQL limpio (Lenovo). El Cable HDMI no tiene marca: devuelve NULL en ambas, sin ningún error.

Enunciado — 2.2: bajar por niveles y arreglos

Solo para el Notebook Aurora 14, obtén: el tipo de almacenamiento (encadenando -> y ->>), los gb de almacenamiento (con #>> y una ruta), el primer_puerto (posición 0 del arreglo puertos) y la cantidad de puertos como cant_puertos (con jsonb_array_length).

🗄️ Ejercicio 2.2 — Rutas y posiciones de arreglo
Resultado
Una sola fila

Deberías ver SSD, 512, USB-C y 3. El arreglo empieza en la posición 0, no en 1.

Enunciado — 2.3: la trampa del tipo (debe fallar)

Quieres los productos con al menos 16 GB de RAM. Escribe SELECT nombre FROM productos WHERE comparando directamente atributos->>'ram_gb' >= 16. Debería fallar.

🗄️ Ejercicio 2.3 — Comparar texto con número (falla)
Resultado
Error esperado

Deberías ver operator does not exist: text >= integer. ->> siempre devuelve text, y PostgreSQL no compara texto con un número.

Enunciado — 2.4: la corrección

Repite la misma consulta, pero convirtiendo el valor a número con ::int antes de comparar (con paréntesis alrededor de la expresión ->>).

🗄️ Ejercicio 2.4 — Convertir con ::int
Resultado
Ahora sí

Devuelve solo el Notebook Aurora 14 (el único producto con ram_gb; los demás dan NULL y no pasan el filtro).

Enunciado — 2.5: por qué importa convertir

Para ver el daño real de comparar como texto, ejecuta SELECT v, v >= '16' AS como_texto, v::int >= 16 AS como_numero FROM (VALUES ('8'), ('16'), ('32')) t(v);

🗄️ Ejercicio 2.5 — Texto contra número, fila por fila
Resultado
El 8 se cuela

En como_texto el 8 sale true: como texto, '8' viene después de '1'. En como_numero sale false, que es lo correcto. Una consulta que "funciona" puede estar mal.

3. Filtrar: @>, ? y compañía

Los operadores propios de jsonb: describes cómo debería verse el documento en vez de recorrerlo.

Enunciado — 3.1: contiene: @>

Escribe tres SELECT nombre FROM productos separados por ;, cada uno con @>: (a) marca Lenovo; (b) almacenamiento con tipo SSD (documento anidado); (c) puertos que incluya HDMI, ordenado por id.

🗄️ Ejercicio 3.1 — Tres búsquedas con @>
Resultado
Tres tablas de resultado

Las dos primeras devuelven solo el Notebook Aurora 14. La tercera devuelve dos filas: el Notebook Aurora 14 y el Monitor Lumen 27. Para buscar un elemento dentro de un arreglo no lo recorres: describes el fragmento esperado.

Enunciado — 3.2: existe la clave: ?, ?| y ?&

Otra vez tres consultas con ;, todas ordenadas por id: (a) productos con la clave garantia_meses; (b) productos con al menos una de las claves bluetooth o inalambrico (?| con ARRAY[...]); (c) productos con las dos claves marca y garantia_meses (?&).

🗄️ Ejercicio 3.2 — ?, ?| y ?&
Resultado
Resultados

(a) Notebook y Monitor. (b) Auriculares y Mouse. (c) Notebook y Monitor.

Enunciado — 3.3: la trampa de los tipos (devuelve 0 filas)

Busca con @> los productos cuyo ram_gb sea el texto "16" (entre comillas dobles, dentro del literal). Después, en el mismo editor, repite la búsqueda con el número 16, sin comillas.

🗄️ Ejercicio 3.3 — "16" frente a 16
Resultado
Cero filas, sin error

La primera consulta no devuelve filas y tampoco lanza ningún error: es el peligro de esta trampa. La segunda devuelve el Notebook. Para jsonb, "16" y 16 son valores distintos.

Enunciado — 3.4: ? solo mira el primer nivel

Comprueba con un solo SELECT sobre el literal '{"a":{"b":1}}'::jsonb si contiene la clave b (columna en_primer_nivel) y la clave a (columna en_raiz), usando ? en ambas.

🗄️ Ejercicio 3.4 — ? en un documento anidado
Resultado
false y true

b está un nivel más abajo, así que ? no la ve (false); a sí está en el primer nivel (true).

4. Modificar sin reescribir todo

Un jsonb no se edita "en el lugar": cada función devuelve un documento nuevo y tú lo guardas con UPDATE ... SET atributos = .... Estos ejercicios cambian los datos: las secciones siguientes y el reto parten del resultado.

Enunciado — 4.1: jsonb_set

Con dos UPDATE sobre el Notebook Aurora 14 usando jsonb_set: sube ram_gb a 32 y después cambia el valor anidado almacenamiento.gb a 1024 (ruta de dos niveles). Cierra con un SELECT que muestre ram (con ->>) y gb (con #>>).

🗄️ Ejercicio 4.1 — jsonb_set en dos niveles
Resultado
32 y 1024

El SELECT final debe mostrar ram = 32 y gb = 1024. Las dos sentencias de UPDATE afectaron una fila cada una.

Enunciado — 4.2: ||, - y #-

Sobre el mismo Notebook, en este orden: (1) con || agrega {"color":"gris","garantia_meses":18}; (2) con - quita la clave color; (3) con #- quita la clave tipo de dentro de almacenamiento. Cierra con SELECT atributos FROM productos WHERE nombre = 'Notebook Aurora 14';

🗄️ Ejercicio 4.2 — Agregar, pisar y quitar claves
Resultado
El documento final

Debe quedar {"marca": "Lenovo", "ram_gb": 32, "puertos": ["USB-C", "HDMI", "USB-A"], "almacenamiento": {"gb": 1024}, "garantia_meses": 18}: la garantía pasó de 12 a 18 (a igual clave gana el documento de la derecha de ||), color ya no está y almacenamiento perdió su tipo.

Enunciado — 4.3: agregar un elemento a un arreglo

El Mouse Pixel tiene colores = ["negro"]. Agrégale "rojo": concatena con || el arreglo actual (atributos->'colores') y guarda el resultado con jsonb_set. Después consulta atributos->'colores'.

🗄️ Ejercicio 4.3 — Sumar un color al arreglo
Resultado
Dos colores

Debe mostrar ["negro", "rojo"].

Enunciado — 4.4: trampa: jsonb_set no crea rutas intermedias

Intenta con jsonb_set poner 6 en la ruta {wifi,version} del Mouse (la clave wifi no existe). Después consulta, con ?, si el Mouse tiene ahora la clave wifi (columna tiene_wifi) junto con su atributos.

🗄️ Ejercicio 4.4 — Ruta intermedia inexistente
Resultado
Sin error y sin cambios

El UPDATE dice que afectó una fila, pero tiene_wifi es false y el documento quedó igual. Como wifi no existe, no hay dónde poner version, y PostgreSQL no avisa.

Enunciado — 4.5: trampa: un NULL de SQL (debe fallar)

Intenta con jsonb_set poner un NULL de SQL (la palabra NULL sin comillas) en la clave marca del Mouse. Debería fallar.

🗄️ Ejercicio 4.5 — jsonb_set con NULL (falla)
Resultado
Error esperado

Deberías ver null value in column "atributos" of relation "productos" violates not-null constraint. Con un NULL de SQL, jsonb_set devuelve NULL para todo el documento, y solo el NOT NULL de la columna lo salvó. Si quisieras guardar un nulo de JSON, se escribe 'null'::jsonb.

Enunciado — 4.6: trampa: el texto sin comillas (debe fallar)

Ahora pon el texto Logitech en marca, pero escribiendo el tercer argumento como 'Logitech', sin comillas dobles internas. Debería fallar.

🗄️ Ejercicio 4.6 — jsonb_set con texto sin comillas dobles (falla)
Resultado
Error esperado

Deberías ver invalid input syntax for type json. El valor debe ser jsonb válido, y un texto necesita sus comillas dobles dentro de las simples: '"Logitech"'.

6. Índices GIN: que no recorra todo el catálogo

Comprueba con EXPLAIN, sobre Postgres real, qué consultas aprovechan cada índice. La tabla tiene solo unas filas, así que el planificador preferiría recorrerla entera: para ver el índice hay que pedirle que no lo haga.

Enunciado — 6.1: un índice GIN y @>

En tres sentencias separadas por ;: (1) crea el índice idx_productos_atributos sobre productos USING GIN (atributos); (2) SET enable_seqscan = off; (solo para esta demostración); (3) EXPLAIN de la búsqueda atributos @> '{"marca":"Lenovo"}' que devuelve el nombre.

🗄️ Ejercicio 6.1 — CREATE INDEX GIN + EXPLAIN
Resultado
El índice se usó

En el plan debe aparecer Bitmap Index Scan on idx_productos_atributos. Ignora los números de cost: lo importante es qué nodos aparecen.

Enunciado — 6.2: el GIN no entiende ->>

Pide el EXPLAIN de la misma búsqueda, pero escrita como atributos->>'marca' = 'Lenovo'.

🗄️ Ejercicio 6.2 — EXPLAIN con ->> (sin índice que ayude)
Resultado
Seq Scan

Ahora el plan muestra Seq Scan on productos con un Filter, aunque el GIN exista. (Verás también Disabled: true, porque apagaste los recorridos secuenciales en 6.1 y aun así no había otra opción.) El GIN solo sirve a los operadores propios de jsonb.

Enunciado — 6.3: índice sobre la expresión

Crea idx_productos_marca sobre la expresión (atributos->>'marca') (paréntesis dobles), repite el EXPLAIN de 6.2 y cierra con RESET enable_seqscan; para devolver el planificador a la normalidad.

🗄️ Ejercicio 6.3 — Índice de expresión + EXPLAIN
Resultado
Index Scan

Debe aparecer Index Scan using idx_productos_marca on productos. Cada tipo de consulta pide su índice: GIN para @> y ?; índice de expresión para igualdad u orden sobre una clave concreta con ->>.

La idea central del reto

¿Sabías que...?

🔤 Desde PostgreSQL 14 hay subíndices

Además de -> y jsonb_set, se puede escribir atributos['marca'] para leer y UPDATE productos SET atributos['marca'] = '"Dell"' para modificar. Hace lo mismo, con una sintaxis más cercana a la de un lenguaje de programación.

🐢 Un Seq Scan no siempre es un problema

Con unas pocas filas, recorrer toda la tabla es lo más barato, y por eso en la sección 6 tuviste que apagar enable_seqscan para ver trabajar al índice. El planificador elige por costo, no por moda.
